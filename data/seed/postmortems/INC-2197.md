## Summary

Checkout began returning HTTP 503 to roughly 40% of requests at 14:12 UTC. The
proximate symptom was `ERR_5012` (`HikariPool-1 - Connection is not available,
request timed out after 30000ms`) on db-prod-03. An engineer had started a
manual `VACUUM FULL orders` outside the change window to reclaim space flagged
by a capacity ticket. `VACUUM FULL` takes an ACCESS EXCLUSIVE lock and rewrites
the table; every checkout write queued behind it, connections were never
returned to the pool, and the pool drained in under three minutes.

## Symptoms

- HTTP 503 on POST /checkout, ~40% of requests
- ERR_5012 / java.sql.SQLTransientConnectionException in checkout-api logs
- checkout-api HikariPool-1 active connections pinned at 50/50, pending > 100
- orders-db pg_stat_activity showing dozens of sessions in `Lock` wait state
- No corresponding deploy or config change to checkout-api

## Root cause

An unscheduled `VACUUM FULL orders` on orders_db (pid 48211) held an ACCESS
EXCLUSIVE lock on the busiest table in the checkout path for 26 minutes. Because
checkout-api holds a connection for the duration of a request, every blocked
request consumed a pool slot until its 30s timeout fired; arrival rate exceeded
timeout rate, so the pool never recovered on its own. pgbouncer was in
`transaction` pool mode and did not shield the application, because the
transactions themselves were the thing blocked.

## Timeline

- 14:08 - `VACUUM FULL orders` started manually on db-prod-03
- 14:12 - first ERR_5012; PagerDuty page to payments-oncall
- 14:19 - checkout 5xx rate peaks at 41%
- 14:31 - blocking session identified via pg_blocking_pids()
- 14:34 - blocking backend terminated; pool recovers within 40 seconds
- 15:38 - incident closed after a clean 30-minute error-rate baseline

## Remediation

1. [diagnose] Identify the blocking session and its waiters `SELECT pid, now()-query_start AS dur, query FROM pg_stat_activity WHERE wait_event_type='Lock' ORDER BY dur DESC` — @priya
2. [diagnose] Confirm the blocker is the maintenance job, not application traffic `SELECT pg_blocking_pids(pid) FROM pg_stat_activity WHERE state='active'` — @priya
3. [fix] Terminate the blocking backend `SELECT pg_terminate_backend(48211)` — @priya (outcome: pool drained back to 6/50 active within 40 seconds, 5xx rate back to baseline by 14:36)
4. [mitigate] Temporarily raise the HikariCP pool ceiling from 50 to 80 to absorb the retry surge — @dan (outcome: reverted at 15:20 once traffic normalized)
5. [fix] Re-run the space reclaim as `VACUUM (ANALYZE)` plus a scheduled `pg_repack` inside the Sunday window — @priya

## Prevention

- Deny `VACUUM FULL` on production via a `pg_stat_statements`-based guard alert
- Add a `pg_blocking_pids` panel to the orders-db dashboard, paging at 60s
- Document the "pool exhausted" triage path in the database runbook
