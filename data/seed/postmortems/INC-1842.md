## Summary

The nightly schema migration ran `CREATE INDEX idx_orders_status ON orders
(status)` without `CONCURRENTLY`. The index build held an exclusive lock on
`orders` for 19 minutes. checkout-api drained its connection pool and returned
`ERR_5012` / HTTP 503 for the duration. Overnight traffic meant customer impact
was limited to about 4,000 failed checkouts.

## Symptoms

- HTTP 503 from checkout-api, ERR_5012 in logs
- HikariPool-1 pending connection requests climbing past 200
- orders-db sessions blocked in `Lock` wait state behind the migration backend
- Migration job `flyway-2024.11.14.01` still running past its 5-minute budget

## Root cause

The migration was authored without `CONCURRENTLY`, which was not caught in
review because the staging dataset was small enough for the build to finish in
under a second. On production `orders` (1.2 billion rows) the same statement
took 19 minutes under an exclusive lock.

## Timeline

- 02:38 - flyway migration starts
- 02:41 - first ERR_5012; page fires
- 02:55 - migration identified as the blocker
- 02:58 - migration backend cancelled
- 03:05 - pool recovered, checkout success rate back to baseline
- 03:52 - index rebuilt with CONCURRENTLY; incident closed

## Remediation

1. [diagnose] Find sessions in Lock wait and their blockers `SELECT pid, wait_event, query FROM pg_stat_activity WHERE wait_event_type = 'Lock'` — @marco
2. [fix] Cancel the running migration backend `SELECT pg_cancel_backend(31904)` — @marco (outcome: locks released, pool recovered within 4 minutes)
3. [fix] Rebuild the index without blocking writes `CREATE INDEX CONCURRENTLY idx_orders_status ON orders (status)` — @marco
4. [mitigate] Pause the nightly migration runner until the rewritten migration was reviewed — @sasha

## Prevention

- CI check rejecting `CREATE INDEX` without `CONCURRENTLY` on tables over 10M rows
- Statement timeout of 5 minutes on the migration role
